# Content rules — what every content step follows

Written by FEAT-104 from design.md §10 (content model and gate), research/decisions.md §4 (transliteration), §7
(sources and attribution), §9 (register rules), R4 §5.3–5.5 (honesty wording) and brief §1, §6, §13, §14. This file
is the authoring contract for the content loop (plan.md §3) and the reference the gate's messages point to.

Three facts frame everything:

1. **Devanagari is the single source of truth.** You author `devanagari`; the build derives `iast`, `easy` and
   `ariaPlain`. Authoring those keys fails the gate (unknown key).
2. **Never type a mantra from memory.** Every mantra/verse carries `source.ref` (an id in `content/sources.json`
   with a URL) and `retrieved`; a record without a resolvable source fails (G4).
3. **Three languages, written by you.** Every prose field is `{ "hi", "en", "bho" }` (G2). Hindi per §6 below,
   Bhojpuri per §7; explanations and retellings are the site's own words (brief §14.3 — the source text may be
   copied in full, the explanations never).

Working copy of the whole corpus for templates and tests: `test/fixtures/content-sample/` (one complete record of
every type — copy from there, do not improvise shapes).

## 1. Files and ids

```
content/
  ui/{hi,en,bho}.json                 UI strings (FEAT-102 owns them)
  termbank.json                       629 terms — glossary ids and display forms; never edit by hand
  forbidden-hi-in-bho.json            G9 lists (hard / soft / allow / latinAllow / patterns)
  sources.json                        { _meta, sources: [ {id, project, title, url, retrieved, licence, kind,
                                        secondSourceAvailable, titles[], note?, wikisourceLang?, encoders?, item?,
                                        publisher?, year?, locator?} ] }
  institutions.json                   Level 0 institutions (name, names[], course, url, status)
  latin-allow.json                    { allow: [...] } proper names allowed in Latin inside hi/bho prose (G8)
  shubhvela-ids.json                  generated by `node tools/shubhvela-ids.mjs` — never edit
  mantras/<group>/<id>.json           ritual-mantra records; <group> = the occasion group that introduces the mantra
  occasions/<group>/<slug>.json       <group> must equal the record's "group"
  texts/<slug>/text.json + <n>.json   text metadata + one chapter per file
  kathas/<slug>/katha.json + <n>.{hi,en,bho}.md
  learn/levels.json, learn/<lessonId>.json + <lessonId>.{hi,en,bho}.md
  glossary/<termbank-id>.json
  reference/<slug>.{hi,en,bho}.md
  static/{about,sources,privacy}.{hi,en,bho}.md
```

Ids: `^[a-z0-9][a-z0-9-]{1,63}$`, equal to the file/folder name. Schemes (plan.md §2.8): mantras `vs-<adhyaya>-<mantra>`
(`vs-36-14-16` for a range), `pgs-<kanda>-<kandika>-<sutra>`, `rv-<mandala>-<hymn>-<verse>`, `pad-<incipit-slug>` (paddhati
verses not in the VS), `pur-<text>-<ch>-<v>`; verses are addressed as `<textSlug>-<n>-<v>`; lessons `l<level>-<nn>-<slug>`
(the `level-` prefix is reserved); glossary ids are term-bank ids; occasion slugs are fixed in `prd.json`. Ids are unique per
collection (G18) — a later occasion that needs an existing mantra references it by id, it never copies the record.

Groups: `foundations daily birth marriage home death kathas vrats festivals shanti`. Layers: `vedic paddhati lok`.
Kinds: `vedic puranic paddhati folk author`. Text `lang`: `sa` (default) · `awa` (Tulsidas) · `hi` (aartis, chalisas,
modern vrat kathas). `verseKind`: `shloka chaupai doha soratha chhand stanza sutra mantra prose`.

Caps (characters per language): title 120 · lede 300 · action 1000 · meaning 4000 · explanation 8000 · note/short 400;
steps ≤ 200, samagri ≤ 150, quiz 3–20 questions. No HTML in any JSON string. JSON prose supports only `[[term-id]]`,
`**bold**`, `*em*`, `[text](url)` and `{{count:…}}`; everything else belongs in Markdown files.

## 2. Record shapes (one full example each — copied from the fixtures)

### 2.1 Mantra / verse — `test/fixtures/content-sample/mantras/foundations/vs-36-3.json`

```json
{
  "id": "vs-36-3", "kind": "vedic", "text": "shukla-yajurveda", "locator": "VS 36.3",
  "title": {"hi": "गायत्री मंत्र", "en": "Gayatri mantra", "bho": "गायत्री मंत्र"},
  "devanagari": "भूर्भुवः॒ स्वः॒ तत्स॑वि॒तुर्वरे॑ण्यं॒ भर्गो॑ दे॒वस्य॑ धीमहि । धियो॒ यो नः॑ प्रचो॒दया॑त् ॥",
  "svara": true,
  "pada": [{"sa": "तत्", "gloss": {"hi": "उस", "en": "that", "bho": "ऊ"}}, "…"],
  "meaning": {"hi": "…", "en": "…", "bho": "…"},
  "explanation": {"hi": "…", "en": "…", "bho": "…"},
  "phalashruti": false,
  "source": {"ref": "ws-syv-36", "retrieved": "2026-10-31", "modified": false},
  "checkedAgainst": [{"ref": "sd-syv-sandhya", "retrieved": "2026-10-31"}],
  "copyright": "pd", "reproduce": true, "copyrightBasis": "ancient Sanskrit; Wikisource transcription CC BY-SA 4.0",
  "tags": ["gayatri", "sandhya"], "review": {"hi": "draft", "bho": "draft"}
}
```

Required: `id kind devanagari svara meaning source copyright reproduce copyrightBasis`. A mantra referenced by any
occasion step is a *ritual mantra* and must also carry `pada` (≥ 1, each `sa` Devanagari-only) and `explanation` (G6).
`variants[]` = `{reading, note{}, source}` where readings differ between sources (use the Madhyandina reading in
`devanagari`). `source.modified` is `false` or a one-line description of what you normalised (ASCII colon → visarga,
`..` → ॥, footnote markers removed). `reproduce: false` is not allowed (G19, brief §14). Chapter verses
(`texts/<slug>/<n>.json#verses[]`) have the same shape minus the registry fields, plus `v` (number), optional
`verseKind`, `speaker` (Devanagari, e.g. `ऋषय ऊचुः`) and `locator`; a verse without `meaning` in all three languages
makes its whole chapter **unpublished** (not rendered, not counted — G7 FLAG).

### 2.2 Occasion — `occasions/marriage/vivah.json`

Required: `id code group phase title lede overview when roles samagri steps sources`. `when = {rules{}, shubhvela:
{muhurat, festival, vrat}}` — ids from `content/shubhvela-ids.json` or `null` (G20; the muhurat ids are the 14 bare engine
ids such as `marriage`, `griha-pravesh`, `mundan`, never `muhurat-marriage`). `roles[] = {role{}, does{}}`.
`samagri[] = {id, item{}, qty, note{}?, must?, searchUrl?}` — `searchUrl` only `https://duckduckgo.com/`,
`https://www.google.com/` or `https://www.bing.com/` with no `tag/ref/aff/affid/utm_*` parameters. `parts[] = {id, title{},
summary{}?}` (every part must own ≥ 1 step; a step's `part` must exist). `steps[] = {n, part?, layer, action{}, mantraIds[]?,
textRefs[{text, chapter | [chapters]}]?, panditSays{sa?, hi, en, bho}?, note{}?, important?, samagriIds[]?, minutes?}` —
`panditSays.sa` is Devanagari-only and may hold `{placeholder}` blanks for the sankalpa (`{गोत्र}`, `{नाम}`). `variants[] =
{region, what{}, source}` (source = a `sources.json` id), `faq[] = {q{}, a{}}`, `sources[]` ≥ 1 ids, `sensitive[]` ⊆
`grief health pregnancy astrology` (the renderer adds the R4 §5.3 rule 4/6 notes — G15 checks the UI strings exist),
`kathaId?`, `textIds[]?`, `tags[]?`, `review`.

Step `action` shape: write it as `<short title> — <prose>` or `<short title>: <prose>` (title ≤ 60 characters, no sentence
inside it). The renderer takes the title as the step heading (h3, step rail, pothi) and shows only the prose under it (an
English prose that starts lowercase after the label is capitalised); the FIRST ` — ` within 80 characters wins over a colon,
so a `label: clause — rest` action gets the whole `label: clause` as its heading — put the dash after the label instead. An
action without such a title is cut at 72 characters for the heading and then repeated in full. Label fields are plain text
(no `[[term]]`, no links, no Markdown): `samagri[].item`, `roles[].role`, `faq[].q`, `panditSays`, every `title`; a
`[[term]]` mark alone as the step title is allowed (the rail shows the term's display form).

### 2.3 Text + chapter — `texts/rudrashtadhyayi/text.json`, `1.json`

text.json required: `id title intro source chapters phase copyright reproduce copyrightBasis`; optional `lang kind deity
author attributionCaveat checkedAgainst vidhiOccasionId tags review`. `chapters[] = {n, title{}, verseCount, locator?}` —
`verseCount` must equal the chapter file's verse count (G7 FAIL); a listed chapter whose file is missing is a FLAG
(not yet authored); a chapter file not listed is a FAIL. Chapter file: `{text, n, title{}, intro{}?, locator?, source,
checkedAgainst?, verses[], note{}?, review?}`. A text whose phase is ≤ the current build phase must have ≥ 1 published
chapter (G7 FAIL). Chapters longer than 40 verses are paginated by the build (`/texts/<slug>/<n>/p2/`…).

### 2.4 Katha — `kathas/satyanarayan-vrat-katha/katha.json` + `1.{hi,en,bho}.md`

`{id, title{}, lede{}, deity, textId?, puranicSource{ref, locator}, caveat{}?, adhyayas[{n, title{}, verseRefs[]}],
vidhiOccasionId, phase, tags?, review}`. `verseRefs` are `<textSlug>-<n>-<v>` of published verses; each adhyaya has
`<n>.{hi,en,bho}.md` with `{{verse:<textSlug>-<n>-<v>}}` panels. Retell in your own words from the Puranic source,
cite the chapter in `puranicSource.locator`, never paraphrase Gita Press prose (brief §6.1).

### 2.5 Lesson — `learn/l0-01-purohit-kaun.json` + `.{hi,en,bho}.md`; `learn/levels.json`

`{id, level 0–4, order, title{}, summary{}, minutes?, quiz[3–20], related{occasions[], mantras[], terms[], texts[],
lessons[]}?, tags?, review}`; `quiz[] = {q{}, options[{id a–d, text{}}] (2–4), answer, feedback{ok{}, no{}}}`.
`levels.json = [{level, title{}, summary{}}]`. Every institution or course named in the prose is a link (G16).

### 2.6 Glossary — `glossary/vivah.json`

`{id (term-bank id), definition{}, related[]? (term-bank ids), occasions[]?, sources[]?, notes? (string, for the owner:
e.g. "evidence: UNCERTAIN"), review?}`. Display forms come from the term bank; you write only the definition.

### 2.7 Markdown files (katha adhyayas, lessons, reference, static)

First line is JSON front matter `{"title": "…", "summary": "…"}`, then a blank line, then the body. Subset
(design §11.3): paragraphs, `#`–`####` (rendered one level lower so the page `<h1>` stays unique), `**bold**`, `*em*`,
`[text](url)`, `-`/`1.` lists, `> ` quotes, `---`, GFM pipe tables, `[[term-id]]`, `{{count:<key>}}`,
`{{mantra:<id>}}`, `{{verse:<textSlug>-<n>-<v>}}`, `{{note:health|grief|astrology}}`, `{{sutra:<mantra-id>}}`.
Internal links are **lang-less site paths**: `[विवाह](/occasions/vivah/)`, `[संकल्प](/reference/sankalpa/)` — the build
prefixes the language (G12 checks them against the route table). Anything else (`<`, raw HTML) is shown as text.

## 3. Sources: fetching, registering, attributing

1. Fetch the Devanagari from the item's sources: Sanskrit Wikisource through the MediaWiki API
   (`https://sa.wikisource.org/w/api.php?action=parse&page=<title>&prop=wikitext&format=json&formatversion=2`, with a
   User-Agent naming the project), sanskritdocuments/stotranidhi with the venv Playwright `page.inner_text("body")`,
   scans by locator. Keep the raw fetch under `$env:TEMP\pb\<phase>\<item>\`. SYV chapter pages 1–9 are zero-padded
   (`अध्यायः ०३`); the Reva-khanda Satyanarayan pages are `…/रेवा खण्डम्/अध्याय:२३३` (colon, no visarga).
2. Normalise only what you record in `source.modified`: ASCII `:` typed for ः, `..`/`।।` for ॥, footnote markers,
   spacing. Keep svara marks when the source has them (`svara: true`); never add or strip them.
3. Register the source in `content/sources.json` if it is new: `id`, `project` (`wikisource sanskritdocuments gretil vhp
   archive stotranidhi kavitakosh titus iitk shubhvela publisher research government other`), `title` (exact page
   title), `url`, `retrieved`, `licence`, `kind` (`copy verify link scan sequence edition portal reference`),
   `secondSourceAvailable`, `titles[]` (every name under which prose may mention it — each such mention must then be
   a link, G16), optional `wikisourceLang encoders item publisher year locator note`.
4. `checkedAgainst[]` is required when the registry entry says `secondSourceAvailable: true` (G4); it names the
   second digital source you compared with (`{ref, retrieved}`).
5. The attribution line is rendered by the build from the registry entry's `project` (decisions.md §7.2): W Wikisource,
   S sanskritdocuments, G GRETIL, V Vedic Heritage Portal / link-only, B modern edition (sequence facts only), T PD scan
   transcription, O other. Do not write attribution text into records.

Owner decision (brief §14): devotional texts are reproduced in full whatever their copyright status; keep
`copyright` (`pd | in-copyright | uncertain`) and `copyrightBasis` truthful anyway, and set `reproduce: true`.

## 4. Devanagari fields (G3)

Allowed in `devanagari`, `pada[].sa`, `panditSays.sa`, `variants[].reading`, `speaker`: U+0900–097F (letters, signs,
danda । ॥, avagraha ऽ, ॐ, Devanagari digits, svara U+0951–0954), Vedic Extensions U+1CD0–1CFF, Devanagari Extended
U+A8E0–A8FF (ꣳ), ZWJ/ZWNJ, space, newline. `{`/`}` only in `panditSays.sa`. Not allowed: Latin letters, ASCII
punctuation (`|`, `.`, `:`), `…`, NBSP, verse numbers (the renderer adds `॥ ३ ॥`). The build also runs the
transliterator over every field and fails on anything it cannot map (e.g. ऑ). U+0953/U+0954 are allowed but FLAGged
(G22: Tiro lacks them).

## 5. Honesty frames (R4 §5.3 rules 1–6; G14)

1. Site voice never asserts an outcome. Frames: `परम्परा में माना जाता है कि …` / `tradition holds that …` /
   `परंपरा में मानल जाला कि …`, or `⟨text⟩ की फलश्रुति कहती है …` with the locator.
2. Never in the site's voice: cures / heals / prevents / treats / diagnoses, "removes disease", "gives a child",
   "guaranteed", "100 %", "scientifically proven"; no Schedule disease name in a sentence whose subject is a
   mantra/puja/vrat and whose verb is curative (that combination is a FAIL; every other seed match is a FLAG for the
   review pack).
3. "उपाय / remedy" only as a translation of what a source says; prefer अनुष्ठान / observance / vidhi.
4. Health, pregnancy, infertility, grief: set `sensitive: ["health"|"pregnancy"|"grief"]` on the occasion — the
   renderer prints the one-line note in all three languages. Astrology pages set `"astrology"`.
5. No financial or legal outcome claims except as a quoted tradition with the rule 1 frame.
6. Phalashruti verses: `phalashruti: true` on the record — they are labelled "फलश्रुति — ग्रन्थ का अपना कथन" and exempt
   from the lint.

Examples (R4 §5.5): ✗ "महामृत्युंजय जाप से रोग दूर होते हैं।" → ✓ "परम्परा में महामृत्युंजय जाप को आरोग्य और दीर्घायु की कामना से
किया जाता है (शुक्ल यजुर्वेद ३.६०; फलश्रुति …)।" · ✗ "Santan Gopal mantra gives children." → ✓ "Couples hoping for a child
traditionally take up the Santan Gopal jaap; the text's own statement of its fruit is given below as the phalashruti."
· ✗ "ई बरत से लरिका होला।" → ✓ "परंपरा में ई बरत संतान के कामना से रखल जाला।"

## 6. Hindi (brief §6.3; decisions §9)

Standard Khari Boli for a family reader. Anusvara for the pancham varna in Hindi prose — पंडित, संकल्प, संस्कार, मंत्र,
अंत, संबंध, शांति; the conjunct forms (पण्डित, सङ्कल्प, मन्त्र, सन्ध्या) belong only inside Sanskrit fields (G10 FAIL).
Nukta ज़/फ़ where the pronunciation has z/f (ज़रूरत, फ़ोन); ख़ only in तारीख़; no क़/ग़. Latin digits. Deities and planets in
the respectful plural. Term-bank spellings (`termbank.json`); where a word exists in Shubhvela's UI that spelling wins.
No Latin tokens except proper names in `content/latin-allow.json` (G8) — add a name there when you need it, sorted.

## 7. Bhojpuri (brief §6.4; decisions §9; G9/G10)

Respectful register: रउआ/राउर; verbs बा/बाड़न/होला/जाला/चलेला/नइखे/करीं/बानी; participles कइल/दिहल/बनल; subjunctive
होखे/जाए/सके; postpositions खातिर/के (never का/की/के लिए); एकरा/ओकरा, अइसन, दुनो, बेसी, नीक, जरूरत; imperatives in -ीं
(करीं, देखीं, सुनीं); no ergative ने. **Hard list (FAIL):** है हैं और या नहीं यह वह अपना/अपनी/अपने आप… की था/थी/थे होता/जाता/करता…
(the full 73 words in `forbidden-hi-in-bho.json#hard`); **patterns (FAIL):** के लिए, की ओर, जाता है, हो गया, माना जाता है,
कहा जाता है; **soft list (FLAG, review):** का (allowed as "what"), ने, गया (allowed as the city), लेकिन, फिर, साथ, नया,
विवाह, व्रत, weekday/month names in Hindi spelling… ण → न in everyday words (कारन, चरन, उदाहरन, परनाम) but ण kept in
mantra words, deity names and shastric terms (गणेश, नारायण, पुराण, तर्पण); nukta only in ड़/ढ़ (जरूरत, तारीख, ब्राउजर — never ज़ फ़ ख़);
UI spellings from Shubhvela: बियाह, बरत, जनम, नाँव, दक्खिन, पूरब, पच्छिम, एतवार…सनिचर, चइत…फागुन. A `bho` string identical to
its `hi` sibling FLAGs over 12 characters and FAILs over 40 (G21) — short shared tatsama headings are fine.

## 8. Glossary marks, counts, sensitive notes, named sources

- Mark glossary terms as `[[term-id]]` the first time they appear in a page's prose (JSON prose or Markdown); the build
  renders the display form in the page language and, on first use, the bracketed alternate (bhoFolk/hiAlt). An unknown
  id is a FAIL (G13); a glossary term left unmarked is FLAGged once per file so you can mark it.
- Numbers about the corpus come only from `{{count:occasions|mantras|verses|terms|chapters|kathas|lessons|texts}}`
  (brief §1); a literal like "193 occasions" FLAGs (G17). Facts of the tradition ("16 संस्कार", "सात पद") are not counts.
- Every named book, text, institution or source in prose is a link (brief §5.1; G16): to the site page when it exists
  (`[रुद्राष्टाध्यायी](/texts/rudrashtadhyayi/)`), otherwise to the registry URL. `sources.json#titles[]` and
  `institutions.json#name/names[]` are the strings checked.
- `{{note:health|grief|astrology}}` inserts the fixed note in Markdown; occasions get it from `sensitive[]`.

### 8.1 Generated blocks on static / reference pages (FEAT-108) — do not repeat them in the prose

- `static/sources.*.md`: the template appends the one neutral brief §14 sentence (UI string `sources.owner_decision`), the
  source registry grouped by project (every entry with its licence link), the fonts block and the build-tools line. Write only
  the introductory prose.
- `static/privacy.*.md`: the template appends the storage-keys table (design §9.3) and the R4 §6.3 GitHub sentences (IP
  logging, Issues). Write the R4 §6.3 paragraph without those two sentences, or keep them — but the table is generated.
- `reference/sankalpa.*.md`: the form (gotra, name) and the worked example are generated below the prose; the example lines
  come from the `sankalp` occasion's `panditSays.sa` — write its placeholders as `{samvatsara} {ayana} {ritu} {masa} {paksha}
  {tithi} {vara} {nakshatra} {yoga} {karana} {gotra} {name}` (labels exist for these keys; any other key shows as `[key]`).
- Lesson / reference / static Markdown may embed `{{mantra:<id>}}` (verse block + meaning + link) and `{{sutra:<id>}}`
  (the quote block); an id that is not in the corpus fails the build.
- Named sources in UI strings are linked automatically from `sources.json#titles[]`; in Markdown prose you still link them
  yourself (G16).

## 9. Review packs (brief §6.4; plan §2.6, §3.5)

Each content item writes `docs/review/<item-id>-bho.md` (≤ 50 EN/BHO pairs from the item, the register decisions you
made, and an "Unsure about" word list — never resolve the owner's word questions yourself) and
`docs/review/<item-id>-hi.md` (20 EN/HI pairs). Every record keeps `review: {"hi": "draft", "bho": "draft"}` until the
owner reads it. Copy the gate's FLAG lines for the item into the pack.

Template:

```
# <ITEM-ID> — Bhojpuri review pack
Written <YYYY-MM-DD>. Records: <ids>. Gate: 0 FAIL, <n> FLAG (listed at the end).
## Pairs (EN → BHO)
1. <en> → <bho>
…
## Register decisions
- <word/phrase>: chose <x> over <y> because <reason / source>
## Unsure about
- <word> — <why>; owner to decide
## Gate FLAGs
<paste of the FLAG lines>
```

## 10. The gate: command, levels, report

```
npm run gate                                  # content/ (or CONTENT_DIR)
node build/gate.mjs --dir <path>              # that directory instead
node build/gate.mjs --dir <path> --lane       # lane mode (section 11)
node build/gate.mjs --phase 2                 # current build phase for G7 (default PB_PHASE or 1)
node build/gate.mjs --dir <path> --dist <dir> # write <dir>/_reports/gate.json instead of dist/
```

**Paths are CLI flags, never persistent `$env:` variables** (brief §15, 2026-11-01: parallel steps share one PowerShell
session, so a `$env:DIST` / `$env:CONTENT_DIR` set by one step changed another step's build). The build takes the same
options as flags, which override the environment for that process only:

```
node build/build.mjs --content <dir> --dist <dir>              # CONTENT_DIR / DIST
node build/build.mjs --base-path / --site-origin https://x.y  # BASE_PATH / SITE_ORIGIN
node build/build.mjs --ci                                      # CI=true (budgets fatal)
node build/build.mjs --content test/fixtures/content-sample --dist $env:TEMP\pb\fx\dist   # a lane / FEAT fixture build
```

`npm run build -- --content <dir> --dist <dir>` passes the flags through npm. Tools keep their own flags
(`tools/audit.py --dist <dir>`). If you find a foreign value in `$env:DIST`, `$env:CONTENT_DIR` or `$env:BASE_PATH`,
remove it (`Remove-Item Env:DIST`) and note it in `status.md`.

Output: one line per finding `LEVEL  file  rule  message`, then `gate OK|FAIL: n FAIL, n FLAG, n WARN`. Exit 0 = no
FAIL; exit 3 = at least one FAIL; exit 2 = a file could not be parsed (`file:line:col`). `dist/_reports/gate.json` is
written **every time** (also on failure, and it is the only thing written to `dist/` on failure): `{generated, ok, dir,
lane, phase, counts:{FAIL, FLAG, WARN}, findings:[{level, file, rule, message}]}`. Read it with

## 11. Lanes (brief §13.2 — three parallel content lanes per phase)

Content items of one phase run in up to three lanes at once. A lane step **never writes inside the repo tree and never
runs git**; it writes its records with the same layout as `content/` into its own staging folder

```
c:\Users\sudiskmr\Downloads\DomainClassification\panditbano\.agents\tasks\v1-build\staging\<A|B|C>\<item-id>\
```

and validates with

```
node build/gate.mjs --dir <that folder> --lane
```

Lane mode differs from the normal gate in three ways:

- **References are WARN, not FAIL, when the target lives nowhere yet.** The gate resolves ids against
  `<dir> ∪ content/ ∪ every staging dir .agents/tasks/v1-build/staging/<lane>/<item>/`. An id found in any of those
  pools passes; an id found in none is a `WARN` (the lane may depend on an item still being written) and the integrate
  step re-runs the normal gate, where it would FAIL.
- **Duplicate ids are FAIL across pools.** The same id (per collection) in `<dir>` and in `content/` or any other staging
  dir fails G18 — lanes are split by domain so this never happens by design; if it does, the lane with the later item
  renames or drops its copy.
- **Registries fall back to `content/`.** A lane folder needs none of `ui/`, `termbank.json`, `forbidden-hi-in-bho.json`,
  `latin-allow.json`, `shubhvela-ids.json`; they are read from the repo. New source entries go into a `sources.json` in
  the lane folder holding only the new entries (`{"sources": [...]}`) — lane mode merges them with the repo registry,
  and the integrate step appends them to `content/sources.json`. New Latin proper names cannot be added from a lane:
  list them in the item findings for the integrate step.

The **integrate step** (single writer) runs, per lane item in `prd.json` order: `node build/gate.mjs --dir <staging>
--lane` → copy the files into `content/` (same relative paths; merge `sources.json` entries; add `latin-allow.json`
names) → `npm run gate` (normal mode, 0 FAIL) → `npm run build` → `npm run test:integration` → one commit
`<ITEM-ID>: <title>`. Review packs (`docs/review/<item-id>-*.md`) travel with the staged files.
